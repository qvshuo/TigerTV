# 优先十源：广告过滤、动态清单及 Android TV 验证

2026-11-16。基于 upstream main `7a4db28dc416447644c79027e37ac7aeef2de310`，本轮结束前用 `git ls-remote` 再次核对。只处理优先十个候选，未继续覆盖其余 18 源；不修改 macOS，不提交、不推送。原有未提交成果保留。

## 1. 实际结论与边界

五源的已确认素材已进入 Android TV 当前清单响应过滤链路：暴风、爱奇艺、360、魔都资源、魔都动漫。五源分别在 Android 14 TV arm64 模拟器上实际联网加载、解码，并完成当前识别区间所有非尾部接缝、音视频渲染、暂停及 1.5 倍速自动测试。没有用模拟清单代替这五项真实播放测试。

本轮有 46 份独立“来源/作品/线路/集”有效 HLS 捕获（复测另计响应数）。五个支持来源中共识别 80 个完整广告组、570 片、时间轴累计 1,504.584 秒。魔都两源六份媒体相同，因此这不是 80 个独立广告素材或独立视频证据；去掉该重复来源为 58 组、1,117.656 秒。爱奇艺微秒时长映射到毫秒产生约 2ms 总舍入差。完整逐清单数据见 `top10-audit-2026-11-16.json`。

**这不是整站广告覆盖率。** 数字仅统计已确认素材在捕获清单中的出现；未对所有整集做人工逐帧审核，未知广告漏报总量无法估计。已抽查的广告首尾及正常剧情负例未发现剧情误删；有限样本不能证明零风险。剧情上的烧录营销横幅保留，无法通过删分片去除。

## 3. 新规则与实证

统一 `KnownHlsAdGroup` 匹配来源、连续 URI 文本 FNV64 向量、每片精确微秒时长、非加密广告段、完整组前后 discontinuity（登记允许末尾的素材可结束于 ENDLIST）。不按固定时间、分片序号、域名通配或单一 discontinuity 删除。URI 带未知查询/片段、组不完整或出现越界重复时回退。

| 来源 | 实现 | 当前样本 | 命中组 / 删除时长 |
|---|---|---|---:|
| 暴风 | `BaofengAdRule.kt` | 3 作品×2集，复用已确认九片素材 | 12 /309.120s |
| 爱奇艺 | `IqiyiAdRule.kt` | 3 作品×2集，登记三套五片完整 URI 向量 | 6 /105.402s（毫秒模型） |
| 360 | `ThreeSixtyAdRule.kt` | 3 作品×2集，同素材两套四片 URI | 18 /316.206s |
| 魔都资源 | `ModuAdRule.kt` | 3 作品×2集，六片与九片素材 | 22 /386.928s |
| 魔都动漫 | 同上 | 同一批六份媒体，不另复制解析器 | 22 /386.928s |

360：两套 URI 各取一组，四片拼接 SHA-256 都为 `9dba3c46f4ace4d794f8d48357bd2d2e2c4f1f2fe7a55afafe724f573f1bb076`。普通剧情 AES-128，广告 METHOD=NONE，广告后恢复原 AES 密钥。已下载、解密相邻正常剧情；没有绕过 DRM。每组 5+5+5+2.567s；尾部广告也匹配，但不虚构尾部后还有剧情。

魔都：六片广告 3+3+5+3+3+0.64s，《嫁金钗》两集各三组；九片素材 3.333+1.667+1.667+2.933+1.667+1.667+1.667+1.667+1.3s，《逐玉》两集各五组、《长安》两集各三组。两个来源捕获到相同清单。六片素材本轮跨来源/跨集成立，未声称该素材已在不同作品出现；九片素材跨作品成立。

爱奇艺：原规则只命中《长安》2/6，另两作品使用不同广告 URI/号码叠字。新增两组分别抽查全部五片首帧及两侧剧情，并离线 WhisperKit 转录，确认是广告后才登记。更新后捕获清单 6/6 均命中；这不保证未来素材覆盖。正常剧情片上存在同样的博彩横幅，明确不删除。

离线转录使用本地 WhisperKit 1.1.1 / multilingual tiny / CPU，单声道16kHz WAV；实际得到“开源旗牌二十年…现在下载集送八百八十八…赶快来玩吧”等有错字口播，配合连续画面复核，不单凭营销词断言。报告将这些标为广告的依据是实际画面 + 口播 + 完整素材组 + 正常剧情边界。

本轮新增窗口至少含 12 个正常上下文分片（360 两窗口、魔都两窗口、爱奇艺两窗口各两片），逐窗口保留。未发现被规则删除的相邻剧情。大量其他保留片只检查 URI/顺序/标签，不计作人工确认的负例。没有以“全部未删除分片”冒充真实负例数量。

## 4. 动态清单

在同一播放地址重新获取：爱奇艺、魔都两源本次代表清单字节未变；360 字节变化且广告位置移动；暴风本轮额外重取超时，保留失败，不用旧成功覆盖该结果。极速、红牛、新浪额外直接 HLS 获取成功，但选取线路不完全同先前比较对象，不做同 URL 稳定性结论。

360《嫁金钗》1 原捕获三段：851.320–868.887、1654.727–1672.294、2925.254–2942.821s；重取为 828.840–846.407、2370.847–2388.414、2925.254–2942.821s。两次均删除相同四片素材的三次出现；**过滤后保留的 1,445 片 URI 顺序完全一致**。这是动态位置下规则可复用的真实证据，不依赖旧时间。若未来 URI 变成未知组则正常播放。

限制：URI 文本不是内容身份的密码学证明。源站若原址替换等时长内容，轻量文本规则无法察觉。当前没有对抗这种服务端行为的保证；需要离线复核和撤销素材数据，不能无边界扩展到目录规则。

## 5. 复杂 HLS、解码与时间轴

`HlsAdFilter.kt` 仅实现当前需要的 VOD TS 子集。支持 METHOD=NONE 与 URI+显式32位十六进制 IV 的普通 AES-128；按保留片继承密钥，未删除正常加密片的有效状态。广告组中的 NONE 被移除，下一剧情仍使用其原密钥；冗余的同一 KEY 不必重复输出。媒体序号必须为0，避免隐式 IV/序列漂移。源清单的尾随 discontinuity 也保留，不无条件删除标记。

MAP、BYTERANGE、隐式 IV、SAMPLE-AES/DRM、未知 KEY 属性、多变体或独立轨道等暂不编辑。真实来源未需要的复杂能力不提前实现。主清单原文保留；只登记无独立轨道的唯一子清单，Media3 仍按原流程加载。子清单当前响应匹配，未额外探测媒体。

真实过滤局部验证：

- 360：原始加密的广告前后两片 + 原始密钥/IV；Kotlin 删去四片广告后，下载保留两片共 962,208 字节，FFmpeg exit0。
- 爱奇艺两组：各七片原始窗口，删五留二；FFmpeg 都 exit0；一组保留2条 SPS buffering-period 警告，不写成零警告。
- 魔都两组：分别八片/十一片窗口，删六/九留二；FFmpeg exit0、无警告。

`EncryptedHlsFixture.kt` 保留真实 1,457 片清单的标签、时长、密钥切换，脱敏 URI/密钥地址。JVM 回归验证删12留1445，保留分片对象（URI、时长、discontinuity、key、encrypted）完全相同，三段原始区间和累计时间映射正确。另验证未知标签、MAP、BYTERANGE、非零序号、隐式IV、素材变更回退、ENDLIST 前标记以及 Android 主/子清单绑定与旧映射清除。

继续复用唯一 `MediaTimeline`。毫秒播放位置→有效剧情时间；过滤播放位置可逆映射回原媒体书签时间。多个删除区间累计偏移；坍缩边界选择广告末尾。当前响应不匹配则会话时间轴清空；切源/集建立独立会话。有效时间不自动等于 danmu_api 参考时间；没有共同剧情锚点时返回未知。本轮没有新增弹幕 UI 或伪造真实弹幕锚点。

## 6. Android TV 实际验证

`LiveHlsPlaybackTest.kt` 使用生产控制器、真实公网 URL、真实 Surface 与音轨，测试时从当前识别的 timeline 读取每个非尾部广告接缝。每次 seek到接缝前1.2s，等待播放越过后1.2s，检查原生音视频输出计数、进度与时间映射；暂停1s进度变化<100ms，恢复1.5倍速并继续播放。尾部删除没有后续剧情，不伪造尾部接缝。

五个独立来源最新一轮全部通过：360 3组/52.701s、魔都《逐玉》5组/87.840s、魔都动漫《嫁金钗》3组/52.920s、爱奇艺1组/17.567s、暴风2组/51.520s。对应过滤后 Media3 duration 为 2,890,120 /2,868,120 /2,890,120 /2,890,120 /2,889,920 ms。首轮及扩大到全部非尾部接缝的第二轮均通过。

保留360和魔都实际剧情截图，360跨过滤边界继续显示剧情。自动检查证明播放器实际解码/输出与进度继续；**没有人工听感结论、没有客观毫秒级音画同步测量、没有电视真机结果，也不是整集从头到尾观看**。没有把 Seek 回调当成功证据。遥控器详细交互复用此前回归，本轮不宣称新增全部交互验收。

## 7. 性能与成本

真实模拟器最新一次媒体清单过滤：暴风45.26ms、爱奇艺40.58ms、36064.50ms、魔都70.68ms、魔都动漫57.56ms。主清单原文处理约5–13ms，网络时间另计。它们是首次解析样本，不是稳定分位数或CPU使用率。

同一360媒体的单次顺序对照：原始首帧2064ms，过滤2564ms；4次PSS采样分别96,739–99,643KiB和97,051–100,819KiB。采样最高差1176KiB。只有一次、非随机化，有网络/缓存噪声，不能把500ms差值全部归于过滤，也不能证明绝无启动影响。PSS是整个播放器进程，不是过滤器独占内存或严格峰值。

不增加普通播放媒体探测请求；主/子清单与分片均为原生播放器原本会请求的内容。超过10MiB响应的回退可能重开同一请求，属于例外。没有客户端FFmpeg、WhisperKit、Chromaprint、AI模型或新播放器依赖。过滤播放进程的两次 `top` CPU 样本为8%和6%（整个进程、模拟器）；未完成可归因的过滤CPU对照，不能虚报“0开销”。

离线研究缓存清理前约330MB（含76.6MB模型、重复媒体拼接与原分片、WAV、关键帧和日志），不随App分发。限制单片8MiB、窗口48MiB，未下载完整剧集；初轮媒体探测256KiB/片。搜索/详情仍调用现有 Kotlin CLI；研究采样脚本不是第二套业务 Core。研究端DNS检查允许公网和已授权代理映射，但没有做连接级DNS pinning，不建议作为通用不可信URL下载服务。

## 8. 可交付状态与后续边界

当前可继续集成和验证的是五源的有限已知素材过滤；红牛、新浪、极速保留原始播放。猫眼证书、如意API是本十源尚未打通的具体网络阻碍，不能靠伪造测试完成。没有理由为这些有限规则部署广告服务或数据库。

下一步仍应围绕这十源：优先补红牛/新浪/极速完整代表内容的广告存在性证据；修复来源端证书/API后再测猫眼/如意；扩充未知素材须先离线确认而非放宽删除条件。已有五源还需要电视真机人工音画验收、较长连续播放和多次首帧性能对照。规则未知/失效时继续正常播放，动态新广告可漏过，不能用误删剧情换覆盖。
